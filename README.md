## Layout

Each plugin is a workspace package under `plugins/<name>/`:

- `src/index.ts` default-exports `Plugin.define({ id, setup })`.
- `package.json` exports the built entry point (`".": "./dist/index.js"`) and
  lists `"files": ["dist", "index.js"]`.
- `dist/` and the root `index.js` shim are generated by `bun run build` and
  committed. Do not edit them by hand.
- `src/*.test.ts` holds `bun:test` tests next to the code.
- `README.md` describes what the plugin does and how to install it.

Plugin ids use the `srobroek.<name>` prefix.

`plugins/lib` is not a plugin. It is the internal `@srobroek/opencode-lib`
package of shared helpers (shell parsing, tool-call targets, test fakes) and is
not released. The build inlines it into each plugin's `dist/`.

### Why plugins ship a bundle

OpenCode installs a `::path:` git spec through npm's Arborist, which packs only
that subdirectory and installs only its registry dependencies. Workspace
packages such as `@srobroek/opencode-lib` are not there at runtime, so
`scripts/build.ts` bundles each plugin with `bun build`. `@opencode/plugin` and
`effect` stay external: OpenCode provides them to plugins and refuses copies
from a plugin's `node_modules`. A local plugin directory is loaded by file name
(`server.*` or `index.*`), not through `exports`, hence the root `index.js` shim.

## Installing a plugin

OpenCode installs a plugin straight from a subdirectory of this repository:

```sh
opencode plugin add 'github:srobroek/opencode-plugins::path:plugins/<name>'
```

Pin a tag (`#<tag>`) to stop automatic updates.

## Claude Code and Codex

The repository is also a Claude Code and a Codex plugin marketplace named
`srobroek-opencode`. It carries only the harness-neutral parts of a plugin:
Agent Skills (`skills/<name>/SKILL.md`) and a bundled `.mcp.json`. Tools, hooks,
agents and TUI code are OpenCode-only and are not exported.

```sh
# Claude Code
claude plugin marketplace add srobroek/opencode-plugins
claude plugin install worktrunk@srobroek-opencode

# Codex
codex plugin marketplace add srobroek/opencode-plugins
codex plugin add worktrunk@srobroek-opencode
```

## MCP servers from plugins

`docs`, `aws` and `design` add MCP servers through `ctx.mcp.transform`, using
`plugins/lib/src/mcp.ts`. Servers are written in the Claude Code `.mcp.json` format,
so the same file ships to Claude Code and Codex; OpenCode-only servers live in code.
In OpenCode:

- A server you configure under the same name in `opencode.json` wins; the plugin
  leaves it alone.
- `${VAR}` and `${VAR:-default}` are expanded from the environment OpenCode starts in
  (OpenCode does not expand `{env:...}` in plugin-set configs), and a server naming
  an unset variable is skipped.
- The plugin option `mcp` is `"auto"` (default: only in projects the plugin's marker
  check matches), `"always"` or `"off"`, and `mcpServers` turns single servers on or
  off by name: `{ "mcp": "auto", "mcpServers": { "storybook": true } }`.
- Every server runs in Code Mode. Remote servers that need no sign-in set
  `oauth: false`; any other remote server signs in through `/mcps`.

## Developing

```sh
mise install
bun install
bun run check   # typecheck, lint, test, build:check
bun run build   # regenerate plugins/*/dist after changing src or lib
```

`bun run build:check` (part of `check` and CI) fails when a committed `dist/`
is stale. Commit the rebuilt output with the source change.
`bun run marketplaces` regenerates the Claude Code and Codex marketplace files;
`bun run marketplaces:check` (also part of `check` and CI) fails when they drift.

Load a local checkout by adding the plugin directory to `plugins` in
`opencode.json`, or link it into `.opencode/plugins/`. Run `bun run build`
after each change; OpenCode loads the built `dist/`, not `src/`.

## Converting Oh My Pi agents

`scripts/convert-agent.ts` turns omp agent markdown into V2 agent markdown:

```sh
bun scripts/convert-agent.ts --out .opencode/agents \
  --fragment model-roles.json ../omp-plugins/delivery/agents/*.md
```

- The omp `@role` becomes the `x-opencode-model-role` request header with the
  model-roles tier it stands for (`cheap`, `standard`, `strong`, `reviewer`), which
  the model-roles plugin resolves to a model. Old role names map to their tier
  (`smol`, `commit`, `tiny` → `cheap`; `task` → `standard`; `slow`, `plan`,
  `architect`, `designer` → `strong`; `challenger`, `judge` → `reviewer`), and
  `default` writes no header. `--role-map map.json` (`{ "<omp role>": "<tier>" }`)
  renames roles first; anything else gets no header and a warning.
- No model is written by default, so without model-roles the agent inherits the
  session's model. `--roles` adds a fallback model per role. A value is
  `"provider/model"`, `"provider/model#variant"`, a model-roles candidate list
  (`["@slow", "provider/model"]`), or `{ "model": "provider/model", "variants": ["low", "high"] }`.
  `thinking-level` becomes `#<variant>` only when the variant is listed.
- The fragment (default `<out>/roles.json`) is `{ "agents": { "<id>": "<role>" } }`
  for the model-roles plugin options.
- `tools` becomes `deny` rules for the V2 actions the agent does not list, and
  listed actions inherit the global rules. Pass `--allow-listed` to emit explicit
  `allow` rules instead, or `--exclusive` for a tool allowlist: a deny on every
  action first, then allows for the listed tools, `skill`, Code Mode (`execute`)
  and, for omp `lsp`, the `lsp_*` MCP tools. A wholly denied tool is left out of
  the agent's requests. `spawns` becomes `subagent` deny `*` plus one allow per
  agent, with `scout` mapped to `explore`.
- A JTD `output` schema becomes a "Report format" section: a `VERDICT:` first
  line and a fenced JSON block.
- Only V2-native frontmatter keys are written. Everything dropped or rewritten
  (omp-only tools, `autoloadSkills`, `skill://`/`rule://`/`agent://`/`proc://`
  references) is printed as a warning.

## Content plugins

Plugins that only ship skills and agents (`debate`, `eli5`, `project`,
`architecture`, `build`, `quality`, `toolchain`, `design`, `agent-coder`) export
`contentPlugin(id, import.meta.url)` from `@srobroek/opencode-lib/content-plugin`. It
registers every `skills/<name>/SKILL.md` and `agents/<id>.md` beside the bundle;
agents are V2 markdown written by `scripts/convert-agent.ts`. They pin no model and
name a model-roles tier in the `x-opencode-model-role` request header. A skill or
agent you already have with the same id keeps its fields.

`bun run agent-roles` (part of `check`) fails when a shipped agent has no tier
header, names a value that is neither a tier nor an accepted old role name, or pins a model outside `delivery`, whose
models are fallbacks for hosts without model-roles. A plugin's `agents/roles.json`
fragment must match the headers.

`bun run steering` (part of `check`) fails on omp steering left in shipped
markdown: `skill://`, `rule://`, `agent://`, `proc://` and other omp URIs, omp tool
names such as `` `bash` ``, `` `task` ``, `` `eval` `` or `ast_grep`, TTSR wording, omp
CLI paths, and SKILL.md frontmatter that is not strict YAML.
